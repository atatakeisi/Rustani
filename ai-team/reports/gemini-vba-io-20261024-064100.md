1. **[高 / 保存・再読込時のメタデータ欠落] インポート済みモジュール（`kind: "document" | "class" | "form" | "object"`）を `automate.saveVbaModule` で編集・保存すると、`kind` が無条件に `"standard"` に上書きされ、モジュール一覧の並び順と大文字小文字も変化する (`crates/engine/src/vba/mod.rs:118`, `121-128`, `146`, `161`)**

## 2. 詳細レビュー

### 指摘1: インポート済み非標準モジュール編集・保存時の `kind` 消失と順序変動

- **結論と影響**:
  - `vbaProject.bin` から読み込まれたモジュールは `crates/xlsx/src/vba.rs:76-93` の `classify_modules` により `"standard"`, `"document"`（`ThisWorkbook` や各 `Sheet`）, `"class"`, `"form"`, `"object"` に分類され、未編集時は `automate.vbaModules` がその `kind` を正しく返す（`crates/engine/src/vba/mod.rs:125`）。
  - しかし、ユーザーがそのモジュール（例: `ThisWorkbook` や `Class1`）をエディタで編集して `automate.saveVbaModule` を呼ぶと、`_gc_vba_sources_v1` には `BTreeMap<String, String>`（名前とソース文字列のみ）が保存され、`save_module` の戻り値（`mod.rs:161`）および保存後の `modules()`（`mod.rs:118`, `124-126`）の両方で `kind` がハードコードされた `"standard"` に置き換わる。
  - さらに `modules()` は `own`（`BTreeMap` の辞書順）をすべて先に出力し、その後で `own` に無い `imported` モジュールを追加するため（`mod.rs:118-127`）、既存モジュールを1つ保存しただけでモジュール一覧の順序が変わり、初回保存時に別ケース（例: `"thisworkbook"`）で保存すると元のインポート名（`"ThisWorkbook"`）のケースも失われる（`mod.rs:146`）。
- **根拠 (`path:line`)**:
  - `crates/engine/src/vba/mod.rs:118`: `out.extend(own.iter().map(|(name, src)| describe(name, src, "gridcraft", "standard")));`
  - `crates/engine/src/vba/mod.rs:124-126`: `!own.keys().any(|n| n.eq_ignore_ascii_case(&module.name))` で `own` にある同名モジュールをスキップし、`module.kind` を引き継がない。
  - `crates/engine/src/vba/mod.rs:146`, `161`: `save_module` が `own` の既存キーのみを検索し、`describe(&key, source, "gridcraft", "standard")` を返している。
- **区分**: **コードで確認**
- **最小再現手順**:
  1. `Document=ThisWorkbook/&H00000000` を含む `vbaProject.bin` を持つブックで `automate.vbaModules` を呼ぶ → `ThisWorkbook` の `kind` は `"document"`。
  2. `automate.saveVbaModule` で `{"name": "ThisWorkbook", "source": "Sub Test()\nEnd Sub"}` を保存し、再度 `automate.vbaModules`（または save 後の reload）を実行する → `ThisWorkbook` の `kind` が `"standard"` に変化する。
- **最小修正案と副作用**:
  - `crates/engine/src/vba/mod.rs:115-162` にて、`d.wb.vba_project` から取得した `imported`（`Vec<VbaModule>`）がある場合、大文字小文字無視で一致する `imported` モジュールの `kind`（および初回保存時の正規 `name`）を引き継いで `describe(..., kind)` を生成する（一致する `imported` が無い新規モジュールのみ `"standard"` とする）。
  - **副作用**: `_gc_vba_sources_v1` の JSON スキーマ（`{"version": 1, "modules": {...}}`）を変更せずに修正できるため、既存ブックとの後方互換性を完全に維持でき、`vbaProject.bin` の保持やエラー時アトミック性にも影響しない。

### 指摘2: `[MS-OVBA]` 仕様に基づく `RawChunk` パディングと `REFERENCEORIGINAL` のパース境界

- **結論と影響**:
  1. **`RawChunk` の末尾 NUL パディング (`crates/xlsx/src/vba.rs:66-68`, `111-120`)**:
     - Microsoft Open Specifications `[MS-OVBA]` §2.4.1.1.5 (`CompressedChunk`) および §2.4.1.3.8 (`Pack CompressedChunkData`) では、非圧縮チャンク（`CompressedChunkFlag == 0`、データ長 4096 バイト固定）の元データが 4096 バイト未満の場合、残りを `0x00` でパディングする規定となっている（2026-10-24 確認: `https://learn.microsoft.com/openspecs/office_file_formats/ms-ovba/`）。
     - 現在 `decompress()`（`vba.rs:111-120`）は 4096 バイトをそのまま `out` に追加し、直後の `read_modules()`（`vba.rs:66-68`）が `if source.contains('\0')` でエラーにするため、4096 バイト未満のソースを `RawChunk` として格納した `vbaProject.bin` が読めない（既存テスト `vba.rs:588-592` は `'x'` × 4096 バイトの `decompress` 単体テストのみで、`read_modules` を通していない）。
  2. **`REFERENCEORIGINAL` (`0x0033`) と `REFERENCENAME` (`0x0016`) の並び順 (`crates/xlsx/src/vba.rs:206-209`, `267-270`)**:
     - `[MS-OVBA]` §2.3.4.2.2.1 (`PROJECTREFERENCES`) / §2.3.4.2.2.4 (`REFERENCEORIGINAL`) では、`REFERENCECONTROL` の前に `REFERENCENAME` が置かれるほか、`REFERENCEORIGINAL` (`0x0033`) の直後に `REFERENCECONTROL` (`0x002F`) が続く場合と、間に `REFERENCENAME` (`0x0016` + optional `0x003E`) が挟まる場合がある。
     - 現在 `vba.rs:206-209` は `0x0033` の直後に `read_control_reference` を呼び、`vba.rs:268` で即座に `c.id(0x002F)?` を要求するため、間に `0x0016` があると `expected 0x002F, found 0x0016` で失敗する。
- **根拠 (`path:line`)**:
  - `crates/xlsx/src/vba.rs:66-68`: `if source.contains('\0') { return Err(...); }`
  - `crates/xlsx/src/vba.rs:111-120`: `if header & 0x8000 == 0 { ... out.extend_from_slice(&bytes[pos..end]); }`
  - `crates/xlsx/src/vba.rs:206-209`, `267-270`: `0x0033` 分岐と `read_control_reference`。
- **区分**: **コードで確認**（実Excelコーパス未実施、MS-OVBA仕様との照合）
- **最小再現手順**:
  - (1) `0x01` + RawChunkヘッダ `[0xFF, 0x3F]` + `"Attribute VB_Name = \"M1\"\r\nSub A()\r\nEnd Sub\r\n"` + 残り `0x00` 埋め（計4096B）のモジュールストリームを持つ CFB を `read_modules` に渡すと `contains a null character` エラーになる。
  - (2) `vba.rs:558` の `references_are_parsed_structurally_before_modules` テストで `0x0033` レコードと `0x002F` レコードの間に `0x0016`（`REFERENCENAME`）を挿入すると `expected 0x002F, found 0x0016` エラーになる。
- **最小修正案と副作用**:
  - (1) `decompress` の RawChunk 分岐（`vba.rs:116`）でチャンク末尾の連続する `0x00` パディングをトリムする（ストリーム途中の不正な `\0` は引き続き `source.contains('\0')` で拒否する）。
  - (2) `read_control_reference`（`vba.rs:267-270`）の先頭で `if c.peek_u16() == Some(0x0016) { skip_reference_name(c)?; }` を許容する。
  - **副作用**: 既存の異常系テスト（NUL混入拒否・不正レコード拒否・出力サイズ上限）を壊さずに互換性のみを広げられる。

### 指摘3: `Compound::stream_path` における Mini-Stream コンテナの毎回再確保

- **結論と影響**:
  - `crates/xlsx/src/cfb.rs:371-377` の `stream_path` は、対象ストリームが `self.mini_cutoff`（4096 バイト）未満であるたびに `let container = self.read_chain(root.start, root.size)?;` を呼び出してルートエントリのチェーン全体を再確保・コピーしている。
  - `crates/xlsx/src/vba.rs:54-59` の `stream_budget`（32 MiB）は返却された `stream.len()`（例: 64 バイト）しか減算しないため、`root.size` が大きい CFB 内に小さなモジュールストリームが最大 128 個（`MAX_MODULES = 128`）あると、`read_modules` 1回の呼び出しで `root.size` 分のバッファ確保・コピーが最大 130 回（`VBA/dir`, `PROJECT`, 128 モジュール）繰り返される。
- **根拠 (`path:line`)**:
  - `crates/xlsx/src/cfb.rs:199-208`, `371-377`
  - `crates/xlsx/src/vba.rs:46`, `51`, `54-60`
- **区分**: **コードで確認**
- **最小再現手順**:
  - `root.size` が 16 MiB で、サイズ 64 バイトのモジュールストリーム 128 個を持つ CFB に対して `read_modules` を呼ぶと、`stream_budget` は約 8 KiB しか消費されない一方で内部的に 16 MiB × 130 回 ≒ 2 GiB の一時 `Vec<u8>` 確保・解放が発生する。
- **最小修正案と副作用**:
  - `Compound` 構造体（`crates/xlsx/src/cfb.rs:20-27`）に `mini_stream: Option<Vec<u8>>` を持たせるか、`stream_path` / `root_stream` で一度構築した mini-stream コンテナを再利用する（または `root_stream` を `open` 時に遅延/一度だけ構築する）。副作用なし。
